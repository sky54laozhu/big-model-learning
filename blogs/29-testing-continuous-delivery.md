# AI 系统的测试与持续交付 —— Prompt 改了一个字，怎么知道没有 regression？

> 一个全栈工程师的大模型学习笔记（二十九）

上一篇结尾我埋了个钩：你改了缓存阈值、换了个降级策略、甚至**只是把 prompt 改了一个字**——怎么知道系统没有偷偷变差？这一篇正面回答它。

这一篇的基调，和上两篇一脉相承：**主角还是你后端的老武器。** CI 流水线、回归测试、灰度发布、版本化、回滚——这些你搭后端时闭着眼都会写。但和上一篇一样，每一件搬到 LLM 系统前面，都得**多挂一条「LLM 独有的新税」**。而这一篇的新税，全都源自同一个你早就认识的老对手——**模型的输出不是确定的**。

我们从一个最小的改动切进去。

---

## 一、绿灯拿什么点？—— `assertEquals` 之死

先锚你最熟的老流程。你改完一段业务代码，到上线之间是这么一条你信得过的流水线：

```
改代码 → git push → CI 跑单测/集成测 → 全绿 → 合并 → 部署（灰度）
```

**绿了就敢发。** 这条线让你放心的底座，是最底层那个东西：

```
assertEquals(add(2, 3), 5)
```

输入定死、输出定死，跑一万遍都一样。红了就是回归，绿了就是没坏。

现在把场景换到你上一篇焊完的那套 LLM 系统（网关、路由、缓存、降级链都在）。你只干了一件极小的事：把系统提示词里的一句话，从「请简洁回答」改成「请用一句话回答」。**一个字都算不上的改动。**

你 push 之前，CI 里那个「绿灯」该拿什么来点亮？你想给这次改动写一条「单元测试」——

```
assertEquals(客服回答, ???)
```

这个 `???` 你**填不出来**。因为大模型的输出不是精确确定的，根本没有一个「期望值」能钉在等号右边。

这就是第 22 篇撞过的那堵墙——`assertEquals` 失效，「对」从一个确定的点，变成了一片语义区域。**你的整套 CI，底座塌了。**

---

## 二、从「等于」到「够好」：换一把尺子

但第 22 篇我们没空手走。那一篇我们造了一把**尺子**——三级判定阶梯：

- **机械判定**（代码能不能编译、schema 合不合法、分类对不对，`===`）
- **语义相似**（余弦相似度，判「跑没跑题」）
- **LLM-as-judge**（叫一个模型当裁判，判「事实对不对、好不好」）

所以最自然的补救是：把 CI 里的 `assertEquals` 换成这把尺子——不判「等不等」，改判「好不好」。

假设我们真这么干了。你改完那个字，把那条客服问题喂进去，尺子打了个分：

```
faithfulness = 0.87
```

盯着这个 `0.87`，麻烦立刻来了：**它算绿灯还是红灯？**

`0.87` 要跟**什么**比，才能叫「有没有回归」？这里藏着两种完全不同的「标准」，得先劈开：

- **A. 一条固定的及格线**：比如「必须 ≥ 0.85 才准上线」。一根钉死的横杆。
- **B. 跟改动前的自己比**：上一版这条 case 是 0.88，你改完变 0.87，那就是「掉了」。

回到你的场景：改完还是 0.87，稳稳超过 0.85——**A 门给你放行了**。可你心里真正怕的根本不是「质量不达标」，你怕的是「**我这一改，是不是让某个本来好好的东西偷偷变差了**」。一个东西从 0.95 掉到 0.86，A 门（≥0.85）照样放行，可它明明退步了。

所以**专门抓「回归」的是 B 门——跟改动前的自己比。** A 门管「够不够好」（质量门槛），B 门管「有没有变差」（回归门槛），这一篇的主角是 B。

B 门要能用，你得先有个「改动前的自己」冻在那儿当参照：**一组固定的输入 + 上一版跑出来的分数**。这就是第 22 篇飞轮里那个**黄金评估集**——现在它的用途升级了，从「离线看看质量」变成了 CI 里那道**回归闸门**。

到这儿，一切都很像你熟的后端 CI 了：冻一组用例、每次改动重跑、跟基线比、掉了就红灯。

**但这里蹲着一只后端 CI 里永远不会出现的鬼。**

---

## 三、那只叫「噪声」的鬼

看现场。你**一个字都没改**，代码原封不动，把黄金评估集连着跑两遍：

```
第一遍：平均分 0.88
第二遍：平均分 0.86
```

代码没动，分数自己抖了 0.02。

麻烦大了：昨天你改那个字，分数从 0.88 掉到 0.87——**你怎么知道这 0.01 是那个字害的（真回归），还是跟上面一样，纯粹是模型这次抽卡手气差（噪声）？**

这只鬼从哪来？源头就是**采样随机性**——temperature 一非零，同样的输入每次采样路径都可能不同（还有个更阴的：如果你的尺子本身是 LLM-as-judge，那**裁判自己也在抽卡**，双份随机）。后端 CI 里 `add(2,3)` 永远等于 5，没这只鬼；你这台机器的零件**天生会抖**。

### 最直接的一味药，治不了本

顺着「是 temperature 惹的祸」这个诊断，最直接的药是：**把评测时的 temperature 设成 0**（贪心解码，每步都取概率最高的 token），随机性不就摁死了？

这药治不了本，两个原因：

1. **设成 0 也不能 100% 复现**（批处理、硬件、MoE 路由都会引入细微不确定性）。
2. **更要命**——你线上真正跑客服时，temperature 是 0 吗？如果不是，那你在 CI 里用 temp=0 测出来的绿灯，保的是**一个你根本不上线的系统**。评测配置必须跟生产一致，否则绿灯没有意义。

结论很硬：**噪声摁不死，你被迫带着它过日子。** 那绿灯到底还怎么点？

你手上有两张牌。

### 第一张牌：别拿单条 case 说事

你那个黄金评估集不是一条，是一整组（假设 200 条）。假设每条 case 的分数都在真值上下随机抖 ±0.05。那这 200 条的**平均分**，抖动幅度会比单条**小**——因为独立的随机误差在求平均时会**相互抵消**一部分，样本越多、均值的抖动越小（大致按 √N 收窄）。

这就是你监控里那条曲线的老道理：**单个请求的延迟忽高忽低，但一分钟的 p99 均线为什么平滑得多。** 同一件事。所以回归判定永远看**一组的聚合分**，绝不看单条。

### 第二张牌：先把噪声地板量出来

哪怕平均了，均线还是会剩一条细细的抖动带——比如它天然在 `0.86~0.88` 之间晃。这条带有多宽，**你不能靠猜，得先量**。

怎么量？简单粗暴：

```
把「一个字都没改」的系统，拿黄金集连跑 5 遍，记下 5 个平均分
→ 看它们自然晃动的范围，比如 [0.86, 0.88]，带宽 ≈ ±0.02
```

这条 `±0.02` 就是你这台机器的**噪声地板**（本底噪声）。有了它，昨天那桩悬案当场结案：

- 改完均分 0.88 → **0.87**（掉 0.01，**在** ±0.02 带内）：**噪声，放行。**
- 改完均分 0.88 → **0.79**（掉 0.09，**远超** ±0.02 带）：**真回归，红灯。**

到这里，那个曾经点不亮的绿灯，判定规则彻底变了一副样子：

![绿灯规则演化图：上下两栏对照。上栏「后端 CI」：一行代码 assertEquals(add(2,3), 5)，标注「单点 · 精确 · 二值（红/绿）」，右侧一个大大的绿色对勾。下栏「LLM 系统」：一个公式框「黄金集平均分 相对基线的跌幅 ≤ 噪声地板 → 绿灯」，标注「一组 · 统计 · 带容差」。框下方两个小例子并排：左「0.88→0.87，跌0.01 ≤ 噪声地板±0.02 → 放行（绿）」，右「0.88→0.79，跌0.09 > 噪声地板±0.02 → 回归（红）」。两栏之间一根向下的粗箭头，箭头旁标「assertEquals 失效（回扣22），尺子从『等于』换成『够好』」。](assets/img/29-green-light-evolution.svg)

> **回归门的新定义**：绿灯不再是「等于」，甚至不是「够不够高」，而是——**跟上一版比，聚合分掉的幅度没超过它自己天生的抖动带。**

## 四、谁动了我的分数？—— 版本化对象炸开

闸门有了。现在戳一个后端 CI 从来不用操心的问题。

后端你 `git` 管的是**代码**——回归的嫌疑人只有一个：你刚提交的那几行 diff。查回归 = 查 `git blame`。

可在你这套 LLM 系统里，能让那 200 条平均分**偷偷掉下去**的东西，真的只有「你写的代码」吗？把整套系统过一遍，嫌疑人是一长串：

```
代码
系统提示词 / prompt 模板   ← 改一个字
模型版本                   ← 厂商可能静默升级
RAG 知识库内容 + 检索配置   ← 换了文档、调了 top-K / 重排（回扣 20/21）
采样参数（temperature 等）
```

任何一样动了，那 200 条平均分都可能塌。而后端那套「查 git blame 抓凶手」在这里**部分失灵**——因为其中最阴的一个嫌疑人，`git log` 里压根没它的名字：

> **模型被厂商悄悄升级。** 你一行代码没 push、一觉醒来，你依赖的那台「零件」自己变聪明了（或变笨了）。

后端世界 `add(2,3)` 永远是 5，绝不会哪天自己变成 6；可你调的模型会。这是 LLM 系统独有的、后端根本不存在的一类回归源。防它的办法：

- **把模型钉到一个钉死的具体版本**（`claude-opus-4-8` 这种写死的版本，而不是 `claude-opus-latest` 这类**浮动别名**——别名会随厂商发布悄悄滚到新版，正是这里要避开的东西；不少厂商还提供带日期后缀的快照 ID，那串日期就是「这一版永不改动」的锁，回扣 26 选型 / 27 网关）。
- **任何一次模型版本变更，都当成一次代码改动，重跑一遍回归闸门。** 它跟你改代码一样危险，只是更隐蔽。

这也顺带解释了：**你为什么非得把上面那一整套配置全「版本化」。** 版本化在这里是**双前提**——

1. **抓凶手的前提**：出了回归，你得能说清「这一版和上一版之间，到底动了 prompt、模型、还是检索」，否则无从查起。
2. **能回滚的前提**：见下一节。回滚回滚的是「哪一版」，没版本化就无从回起。

![版本化对象炸开图：中央一个圆圈标「那 200 条平均分为什么塌了？」，周围五个方框像嫌疑人一样用箭头指向它。五个方框：①「代码 diff」标注『后端唯一的嫌疑人 · git blame 可查』；②「系统提示词（改一个字）」；③「模型版本」用红色高亮，标注『⚠️ 厂商静默升级 · git log 里没有它 · 你没 push 任何东西它自己就变了』；④「RAG 知识库 + 检索配置（回扣20/21）」；⑤「采样参数 temperature」。图底部一根横条写「版本化 = 钉住这一整套 → 既是抓凶手的前提，也是能回滚的前提」，并把模型版本框旁边补一小标签「钉到钉死的具体版本 claude-opus-4-8，别用 latest 浮动别名」。](assets/img/29-versioning-suspects.svg)

## 五、离线全绿，也不等于线上没事

版本化 + 回归闸门，这套**离线防线**成型了。但还有最后一道坎。

你的黄金评估集是**你亲手冻的那 200 条**。改动过了闸门、全绿，你推上线——为什么线上还可能出事？

因为**你那 200 条离线用例是死的，真实用户砸进来的输入分布永远更野**。离线全绿只证明「相对上一版没退步」，不证明「线上不会炸」——总有你没想到的问法、没覆盖到的场景。所以持续交付这一侧，得靠两件事接住这条鸿沟。

### 一、灰度发布：别让炸的时候一发全崩

这是你后端的老武器，原样搬来就能用：新版先切 **5% 真实流量**，稳了再一档档放量到 100%，指标一塌立刻踩刹车。这样哪怕真踩雷，也只炸一小撮用户、你还来得及回滚。

### 二、线上监控：拿什么当「被监控的分数」？

离线你可以慢悠悠叫 LLM 裁判给 200 条打分。可线上每秒几百条真实请求，你**没法**对每一条都叫个裁判来打分，两个原因：

- **成本**：每条都判，等于把请求量翻倍烧钱。
- **更根本**：线上那条真实请求，**你手上没有「标准答案」可比对**，裁判无从判起。

所以线上退而求其次，盯一批**行为代理信号**——共同点是「不需要标准答案，从用户的动作反推质量」：

| 信号 | 变差时的样子 |
|---|---|
| 点踩率 ↑ | 用户直接说「这答得烂」 |
| 追问率 ↑ | 同一件事反复追问 = 一次没说清 |
| 转人工率 ↑ | 用户放弃 AI 去找真人 = 系统答不动 |
| 会话放弃率 ↑ | 问一半跑了 |

这正是第 22 篇飞轮的分工：**离线黄金集打精确分，线上代理指标看趋势。**

### 回滚：这里有个 LLM 独有的拐弯

后端回滚 = `git revert` 代码。可你这里闯祸的也许**根本不是代码**——而是第四节那个静默升级的模型、或改坏的 prompt、或换了的知识库。所以你的「回滚」是**把整套配置钉回上一版**。这就闭环回上一节：**没版本化，你连回滚到「哪一版」都说不清。**

## 六、收口：把尺子焊进发布线

第五阶段问的是「怎么把 AI 系统的架构搭对」。这一篇给的是**测试与持续交付**这根支柱，而它的骨架**依然全是你后端老规矩的平移**，只在几处挂上 LLM 新税：

> `assertEquals` 失效（回扣 22）→ 换成第 22 篇那把「尺子」→ 分清 A 及格线 / B 基线对比，回归归 B → 但采样随机这只「噪声鬼」摁不死（temp=0 治不了、配置必须对齐生产）→ 两张牌：**聚合一组**（√N 收窄）+ **量噪声地板** → 新绿灯 = **跌幅 ≤ 噪声地板** → 能让分数偷偷塌的嫌疑人一长串（prompt / **模型静默升级** / RAG / 检索 / 参数）→ **版本化**整套配置，既为抓凶手也为能回滚 → 离线绿 ≠ 线上安 → **灰度 5% + 线上代理指标**（点踩/追问/转人工）→ 回滚 = 钉回整套配置。

**harness 暗线收口**：第 22 篇给了你一把「尺子」（评估 = 柱子三「驯服不确定性」的度量落地）；这一篇就是**把这把尺子焊进发布管线**，让「改动 → 绿灯 → 灰度 → 观察 → 回滚」这个飞轮自己转起来。

再往深一层——这跟 agent loop 里的「校验 + 重试」（第 18 篇）是**同一个工程思想在不同尺度上的两次出现**：

- **单次调用尺度**：你用 schema 校验，兜住会抖的**一次输出**。
- **发布尺度**：你用回归闸门 + 灰度，兜住会抖的**一次改动**。

都是柱子三那句话——**用确定的手段，兜住会抖的零件。** 只是零件从「一个 token」放大成了「一次上线」。

下一篇，我们从「系统会不会变差」转到「系统会不会被人搞坏」：用户会想方设法绕过你的规则——让模型说不该说的、做不该做的。也就是 AI 系统的**安全与防护栏设计**：怎么防止用户绕过你的安全策略。

## 小结

- **核心直觉（后端迁移）**：CI、回归测试、灰度、版本化、回滚全是后端老武器。这一篇的所有「新税」都源自同一个老对手——**模型输出不确定**。
- **`assertEquals` 之死**：改一个字的 prompt，等号右边填不出「期望值」→ 回归测试的底座塌了（回扣 22）。
- **换尺子 + 分清两道门**：用第 22 篇的尺子判「够好」而非「等于」。**A 及格线**管质量、**B 基线对比**管回归——回归门是 B（跟改动前的自己比）。参照物 = 黄金评估集升级成 CI **回归闸门**。
- **噪声这只鬼**：采样随机（+ 裁判也是 LLM 的话双份随机）让同样代码跑两遍分数都不同。temp=0 治不了本（不完全复现 + 必须对齐生产配置）。
- **两张牌点绿灯**：① **聚合一组**（200 条平均分按 √N 收窄抖动，别看单条）；② **量噪声地板**（不改动连跑 N 遍看自然带宽）。新绿灯 = **聚合分相对基线的跌幅 ≤ 噪声地板**。
- **版本化对象炸开**：后端只管代码；LLM 系统里嫌疑人一串——prompt、**模型（厂商静默升级，git log 里没有它）**、RAG 知识库、检索配置、采样参数。钉模型到钉死的具体版本（别用 `latest` 这类浮动别名），任一变更都重跑闸门。版本化 = **抓凶手 + 能回滚**的双前提。
- **离线绿 ≠ 线上安**：黄金集是死的、真实分布更野。**灰度 5%** 限制爆炸半径；**线上代理指标**（点踩/追问/转人工，因为线上没法逐条叫裁判：成本 + 无标准答案）看趋势。回滚 = 把整套配置钉回上一版。
- **harness 暗线**：把评估尺子焊进发布管线 = 柱子三驯服不确定性；与第 18 篇「校验 + 重试」同构，只是从单次调用尺度放大到发布尺度。
