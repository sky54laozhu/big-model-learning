# 韧性设计与成本工程 —— 模型挂了怎么办？token 费用怎么控制？

> 一个全栈工程师的大模型学习笔记（二十八）

上一篇结尾我埋了个钩：当 AI 的请求量、成本、延迟都开始变成真问题时，**缓存**这把老武器该怎么用在 LLM 上？这一篇正面回答它，顺带把上一篇只点到、没展开的 **failover** 也一并挖开。

先打个预防针，这一篇的基调和上一篇一模一样：**几乎不发明任何新东西。** 韧性那套武器——重试、failover、降级、熔断——你搭后端时闭着眼都会写；缓存你更是天天用。这一篇真正的教学点只有一句：

> 这些祖传武器搬到大模型前面时，**每一件都得多挂一条「LLM 独有的新税」**。

你会看到的，全是「老武器 × 新账单」的对照。

## 一、重试：老武器，第一张新账单

先摆一个你无比熟悉的场景。你的订单服务要调下游的支付网关，下游偶尔抽风——超时、502、被限流。你手里有一整套祖传武器：**重试（带退避）、熔断、降级、缓存**。

现在把「支付网关」换成「大模型 API」。表面上还是同一个故事：一个会抽风的外部服务，你要让自己别跟着一起倒。所以第一直觉是——**把这套武器原样搬过来就完了。**

但先卡住一个问题：支付网关抽风你重试，几乎没代价——请求便宜、幂等、快。换成大模型，一次重试跟原来比，**性质上有三样变了**：

- **钱**：大模型每调一次都是真金白银。重试三次 = 烧三次钱。重试策略从「尽管试」变成「试之前先算账」。
- **时间**：大模型本来就慢（回扣第 13 篇的 TTFT + 逐 token 解码，一个请求几秒到几十秒）。你做「带退避的重试」，退避是要等的——支付网关重试用户没感觉，大模型你重试一轮，用户可能**干等小一分钟**还在转圈。退避越稳，体验越崩。
- **结果**：这个最微妙，直接顶上你后端的老词——**幂等性**。你对同一个 prompt 重试，两次拿到的回答**不一样**。

第三点得拆开看，因为它决定了重试到底安不安全。你可能担心「回答不一样」——但抬个杠：帮我写段文案，重试拿到**措辞不同**的一段，算个事吗？不算。**纯文本生成，答案换个说法基本无害。** 那第二次重试的真牙齿长在哪？两颗：

- **牙齿一（钱）**：模型已经在跑了，你这边超时断开重发——第一次那半截生成，很可能**照样计费**。你为一个没收到的回答付了钱，再花一次钱重来。
- **牙齿二（副作用）**：如果这次调用不是纯生成，而是模型**已经触发了一个工具调用**——已经让 harness 发了封邮件、扣了一次库存（回扣第 24 篇「坏 = 不可逆动作」那道护栏）——你一重试，**邮件发两封，库存扣两次**。

看出门道没：**重试安不安全，不取决于大模型本身，取决于这次调用有没有带副作用。** 纯生成随便重试（顶多多烧点钱）；一旦挂着会改变世界的工具，重试就得跟你后端处理「重复下单」一个级别地小心——幂等键、去重、或干脆不自动重试。

所以「重试」这颗零件，得先能回答：**这次失败，是哪一类失败？** 而这张分类表，跟你后端重试 HTTP 用的是**同一张**：

| 错误 | 该重试吗 | 为什么 |
|---|---|---|
| `429 Too Many Requests`（被限流） | ✅ 退避后重试 | 暂时性、不怪你，等一下就好 |
| `500 / 连接超时`（且本次纯生成、无副作用） | ✅ 可重试 | 暂时性抖动 |
| `400 Bad Request`（prompt 拼错、schema 不合法） | ❌ 别试 | 确定性错误，重试一百次还是同一个错，纯烧钱 |
| 任何带副作用的调用 | ⚠️ 慎试 | 见牙齿二，得先解决幂等 |

**能重试的都是「暂时性、不怪你」的错；不能重试的都是「确定性、就是你错了」的错。** 分类逻辑跟后端一模一样，LLM 变的只是**判错的代价（烧钱）**和**副作用的凶险**。

还有个 LLM 独有的超时坑，顺带说透：后端那种「3 秒硬超时」直接搬过来，会把大量**正常的慢请求**误杀成超时、白白触发重试（回扣第 13 篇——LLM 本来就慢）。尤其流式响应，正常就要几十秒——不能卡「总时长」，得拆成两个超时：**首 token 超时**（多久没吐出第一个字才算挂）+ **token 间隔超时**（吐着吐着卡住才算挂）。

## 二、failover 与降级链：换厂商不是平移，是降级

盯住 `429` 再挖一层，因为「重试」在这里是个岔路口。被限流了，你手上有两条路：

- **路 A**：原地退避，等 2 秒、4 秒再问**同一家**（Anthropic 说我忙，那我等等再求它）。
- **路 B**：这家忙？我**换一家**问去（Anthropic `429`，直接甩给 GLM）。

路 B 你眼熟——就是上一篇点到、没展开的 **failover**。而且上一篇给它安了家：网关手里攥着一张「厂商 / 模型清单」，路由和 failover 都住在**网关的控制流层**。

那 failover 换厂商，是**免费**的吗？不是。你把一个为 Claude 精调过的 prompt 甩给 GLM——它是**另一个模型**，回答质量会变、格式可能不照你的指令走、连结构化输出的脾气都不一样（回扣第 27 篇「异构外人」）。你换来了「系统还活着」，付出的是「这次回答没那么好」。

也就是说：**failover 换厂商不是平移，是降级。** 而「降级」这个词，把我们抬到一个更大的武器上——**优雅降级（graceful degradation）**。

后端的降级你太熟了：下游挂了，与其甩用户一个 500，不如**给个兜底的、次好的东西**。核心思想一句话：**宁可给差的，不给崩的。**

关键洞察是：**「换厂商 failover」只是降级菜单上的一道菜，不是全部。** 大模型的降级菜单比后端更丰富，因为「下游」本身可以挑档次。按「牺牲多少质量」从少到多排一排，就是一条**降级链**：

| 档 | 动作 | 牺牲 | 回扣 |
|---|---|---|---|
| 1（降得最少） | 换**同厂商更小的模型**（Opus → Haiku） | 质量掉一点，还是它自家的 | 第 26 篇「模型大小轴」往下滑一格 |
| 2 | 换**别的厂商**（failover） | 质量跳变更大 | 第 27 篇异构 |
| 3 | 给个**缓存里的旧答案** | 可能过时 | 本篇下半场 |
| 4（彻底降） | 写死的**兜底话术**「系统繁忙」/ 直接关掉 AI 功能走老路径 | 没有 AI 了 | — |

这四档的共同规律：**守住了「可用」，牺牲了「质量」。** 所以设计上有个自然动作——**永远从「降得最少」的那档开始试，扛不住再往下摔一格**。Opus 挂了先滑 Haiku，Haiku 也不行才换 GLM，全挂了才吐兜底话术。

这里得把两条轴分清，别绕成一个圈：**扳机是「事件」，降级链是「响应」。** 触发这条链的事件有仨——熔断跳闸、**某厂商 429 / 挂了**、以及下半场你会看到的**预算撞顶**；而「换厂商 failover」本身是链上的档 2，是**响应动作**，不是扳机。同一条链，多个事件都能触发它。

![降级链阶梯图：一段从上往下的四级台阶，代表「质量从高到低、可用性始终守住」。台阶从上到下依次是：档1「Opus → Haiku（同厂商滑小模型，回扣26）」、档2「换厂商 failover（异构，回扣27）」、档3「返回缓存旧答案」、档4「写死兜底话术 / 关闭 AI 功能」。右侧一根竖直箭头标注「质量 ↓」，左侧一根横杠标注「可用性 —— 始终守住」。台阶左侧三个扳机指向整条链：「熔断跳闸」「厂商 429/挂了」「预算撞顶」，点明同一条降级链有多个触发器。底部一行口诀：宁可给差的，不给崩的——永远从降得最少那档往下摔。](assets/img/28-degradation-ladder.svg)

## 三、熔断：别一次次去撞一堵已知的墙

降级链有个前提问题没答：Opus 挂了滑 Haiku——你**怎么知道** Opus 挂了？

朴素做法是：每个请求照常发给 Opus，等它超时，再降级。但如果 Opus **持续挂了五分钟**，这五分钟里进来的**每一个请求**，都要先老实实地**付一次超时的钱和时间**，撞完墙才降级。用户每个白等 30 秒，你每个白烧一次 token。

这个「别再撞一堵已知的墙」的老武器，你家电路里就有——短路了谁跳闸？**空气开关 / 保险丝**，英文 **circuit breaker**，中文叫**熔断器**。后端把它搬来防「雪崩式重试一个死服务」，就叫**熔断**。它有三个状态：

- **闭合（closed）= 正常放行**：请求照发。它一边放行一边数最近失败率，超阈值（比如 10 秒内挂了一半）就准备跳。
- **断开（open）= 跳闸了**：失败率爆表，「啪」跳闸。接下来一段时间（比如 30 秒），**请求根本不发给 Opus 了**，直接快速失败、直接走降级链。这就治好了上面那个病——跳闸后一个请求都不去撞墙了。
- **半开（half-open）= 小心试探**：跳闸 30 秒后面临两难——不敢直接合闸放全部流量（万一还没好等于又一次雪崩），也不能永远断着（万一早好了白白降级亏质量）。折中办法：**放一个探针请求（single probe）**进去。探针**成功** → 合闸恢复全量；探针**失败** → 立刻再跳闸冷却。妙在它只赌**一个**请求的钱，就换来「要不要恢复全量」的判断。

到这，韧性半篇的四件套齐了，收个口——**它们全是你后端的祖传武器，一件没新增**：

| 武器 | 后端老用途 | 搬到 LLM 唯一变的那点 |
|---|---|---|
| 重试 | 扛暂时性抖动 | 要先算钱账 + 防副作用重复（回扣 24） |
| failover | 换个下游实例 | 换的是**异构厂商**，质量会跳变（回扣 27） |
| 降级链 | 宁给差的不给崩的 | 菜单更丰富：滑模型档（回扣 26）→ 换厂商 → 缓存 → 兜底 |
| 熔断 | 别撞已知的死服务 | 半开探针那一下也是**花钱**试探 |

**一句话暗线**：韧性这半篇没发明任何新东西，只是把 API Gateway 的老武器搬进**网关控制流层**（回扣第 27 篇的分层解剖）——但每一件武器扣动扳机前，都多挂了一个 LLM 独有的顾虑：**这一下值不值这个钱、会不会把世界改两次。**

## 四、缓存翻面：从应急 Plan B 到省钱正职

上面降级链的档 3 是「返回缓存旧答案」——在那儿，缓存只是个**应急 Plan B**：模型挂了才掏它。现在把它翻过来，因为缓存真正的分量在别处。

先锚你后端最熟的画面：一个热点查询，同样的参数一秒被请求一千次。你不会真去查一千次数据库——前面挂个 **Redis**，第一次查完按 `key` 存住，后面 999 次直接命中缓存。**注意：这时候数据库好得很，没挂。** 你上缓存纯粹是为了**性能**。

性能是对的一半——缓存命中几毫秒返回，省掉大模型那几秒的等待，对本来就慢的 LLM 体验提升巨大。但最狠的那个字，是本篇开头就说过的：**每调一次都有成本。**

数据库缓存命中，省的是 CPU 和 IO，本也不太值钱。大模型缓存命中，省的是**一次真金白银的 API 账单**。所以对 LLM 来说：

> **缓存的头号正职是省钱，性能（低延迟）是搭着一起赚的。**

这就是上一篇那句「相同问题能不能不重复烧钱问模型」的正面回答——**能，只要你认得出这是同一个问题。**

## 五、精确缓存的裂缝，与语义缓存

盯住「认得出」。key 拿什么当？顺着 Redis 的思路，最直接的答案是把**决定输出的整个输入**哈希一把当 key——`hash(model + 完整 messages + temperature + ...)`，命中就直接返回上次的答案。这叫**精确缓存（exact-match cache）**。

它能跑，但有一道裂缝。用两个请求逼你看见：

- 用户 A 问：`「什么是 RAG？」`
- 用户 B 问：`「RAG 是什么？」`

这俩在你我眼里是**同一个问题**。可你用 `hash(字符串)` 当 key——差一个字、调个语序，hash 就变，**这俩不会命中同一条缓存**。精确缓存认的是**字节**，不是**意思**。

修法几乎是白给的，因为「认出两句话意思一样」这件事，我们早在第 19 篇就造过零件了：**把句子染成向量，意思近的箭夹角小、余弦大。** 所以：

> 别拿 `hash(字符串)` 当 key。把 query **染成向量**，去缓存里做一次**余弦相似度检索**——找到一条**足够像**的历史问题，就把它的答案返回。

这叫**语义缓存（semantic cache）**。本质上就是**把第 19 篇的语义搜索对准缓存自己**：缓存从 key-value 精确查表，变成一个小型向量库，命中判据从「字节全等」松成「意思够近」。这正面回答了上一篇第二个钩子——「语义相近的问题缓存还认得出吗」——**认得出，靠 embedding。**

**但是。** 你把命中判据从「全等」松成「够像」，我立刻担心一件事，而且这件事在第 19、22 篇都埋过雷、画过 ⚠️：

> `「我要退款」` 和 `「我不要退款」`。

`退款`这个主题把两句话的向量往一块儿拽，`不`这一个字的反向语义**扛不过主题的拉力**，于是夹角很小、余弦很高——语义缓存一看「够像」，**把 A 的答案端给了 B**。掂量一下这个坑的**严重性等级**，它跟「缓存没命中」根本不是一个量级：

- **缓存 miss**：顶多白花一次钱去问模型，用户拿到的还是**对的**答案。代价只是钱。
- **语义缓存命中错答案**：你把「怎么退款」的教程，端给一个刚说「我**不**要退款」的人。用户拿到一个**自信的错答案**，而且最阴的地方——**你还省了钱、系统一切正常、日志上根本看不出模型没被调用**。你是**省钱省出了一场事故**，无声无息。

所以语义缓存不是免费午餐：它拿**正确性**这个硬东西，换**省钱 + 提速**。又是一次**约束下的权衡（柱一）**。而权衡就得有个**旋钮**——那就是**相似度阈值**：

- 阈值**拧高**（很像才命中）→ 误判少、安全，但命中也少、**省不下几个钱**。
- 阈值**拧低**（差不多就命中）→ 命中多、省钱猛，但「退款 / 不退款」这种越容易端错。

这颗旋钮拧到 0.85 还是 0.95，**凭什么定？别拍脑袋**——用第 22 篇那把尺子。搭个黄金集（一堆「该命中 / 不该命中」的问题对），把阈值从 0.80 扫到 0.99，盯两个指标：**命中率**（省了多少）和**错误命中率**（闯了多少祸），挑那个「错误命中率压到你能容忍的红线以下、命中率还尽量高」的点。医疗 FAQ 红线 near-zero 就得拧很紧；闲聊机器人容错高就能拧松。**阈值不是玄学数字，是拿尺子量出来的。**

生产里的标准做法是把两者叠成**两层缓存**，各展所长：

- **L1 精确层**：先 `hash(字符串)` 查一把。命中最好——**零误判风险、几乎零成本**，同一个问题一字不差地重复问走这条快车道。
- **L2 语义层**：L1 没中才落到向量检索。省钱大头在这层，风险也全关在这层。

好架构——它把危险**锁进 L2**，L1 永远安全；但它甩不掉那颗阈值旋钮，只是把旋钮挪进了 L2。

![语义缓存流程图：一个请求进来，先走「L1 精确层：hash(字符串) 查表」，标注「零误判 · 命中即返回」；miss 后落到「L2 语义层：query 染成向量 → 余弦相似度检索」。L2 中间画一个旋钮标注「相似度阈值」，旋钮两侧标：往高拧「安全但命中少、省钱少」、往低拧「命中多、省钱多但易端错」。旋钮下方一个小坐标图，两条随阈值下降的曲线「命中率（省多少）」与「错误命中率（闯多少祸）」，标注「拿第22篇黄金集扫阈值定这个点」。右侧一个红色 ⚠️ 卡片：反义句坑——「我要退款」vs「我不要退款」主题相同、向量很近、余弦高 → 命中错答案；比 miss 严重得多：省钱省出一场无声事故（回扣19/22）。](assets/img/28-semantic-cache.svg)

## 六、可缓存性：不是所有请求都配缓存

语义缓存修的是「意思一样却认不出」。现在给你**第二个坑**，它跟「语义」半毛钱关系没有——

> 两个用户，都问 `「我的订单到哪了？」`，**一字不差**。

精确缓存一看字符串全等，hash 相同，**命中！** 把上一个用户的答案端出来。这次命中，**对吗？** 你肯定摇头。可这个坑正相反——是「**字符串一样却不该共享答案**」，语义缓存在这儿**一点忙帮不上**（它俩向量完全重合，命中得更欢）。

`「我的订单到哪了」`不能缓存，有**两个独立原因**：

- **时效性**：同一个人早上问、晚上问，答案不同 → key 得**带时间**。
- **个性化**：用户 A 和 B 同一分钟问出**一模一样**的字符串，答案该是**各自的订单** → key 还得带**「谁在问」（user-id）**，甚至那份实时查出的订单数据本身。

而一旦你把 user-id、实时数据全塞进 key，会发生很讽刺的一幕：**这个 key 几乎永远不会重复命中**——因为你把「每次都在变的东西」都编进 key 了。硬结论：

> **个性化 + 实时数据的请求，本质上就不该在响应层做缓存。**

那什么才**天生适合缓存**？两个特征缺一不可：

1. **答案稳定**：不随人、不随时间变。
2. **高频重复**：缓存收益 = 命中次数 × 每次省的钱。一个答案再稳定，全世界只问过一次，命中次数 = 0，收益 = 0，你还倒贴了存储和向量化成本。

这又是第 26 篇的**二八长尾**：少数热门问题占掉大部分流量，你缓存那**一小撮高频稳定问题**（FAQ、产品定义、文档热门问答），就吃掉了大部分省钱空间。

最后补一个运维现实：**「稳定」只是相对的。** 退货政策从 30 天改成 15 天、产品文档改版，缓存里那条旧答案就**脏了**，还会被自信地一直命中返回——这是「省钱省出事故」的另一个来源。所以缓存必须配**失效策略**：最省事的是 **TTL**（给每条缓存设个生存期，到点自动作废，FAQ 类几小时到几天）；要求实时正确的（政策 / 价格），则底层数据一改就**主动按 key / 标签清掉**对应缓存。⚠️ 语义缓存里的脏答案更阴——它跨一片相似问题命中，一条脏数据能污染一大片，比精确缓存难清得多。

## 七、prompt caching ≠ 响应缓存

还有一种缓存，名字里也有「缓存」，但跟上面聊的**响应缓存是两码事**，很多人会混——Anthropic 的 **prompt caching（提示缓存）**。要看懂区别，回扣第 13 篇。

先把第 13 篇的画面调出来：模型处理请求分两阶段——**prefill**（把你**整个 prompt** 的每个 token 都算一遍 K/V，塞进 KV Cache）+ **decode**（逐 token 往外吐）。「首 token 慢」就慢在 prefill 要把整段输入嚼一遍。

现在一个典型的 RAG / Agent 场景：你**每个请求**，prompt 最前面都雷打不动塞着同样一大坨——2000 字 system prompt + 一堆工具定义 + 大段固定背景资料，只有最后那句用户问题在变。那么每来一个请求，模型的 prefill 对这**前面完全相同的前缀**在干嘛？——**把同一段前缀的 K/V 从头重算一遍。** 同样的 K/V，算了一遍又一遍。

**prompt caching 就是把这段固定前缀的 KV Cache 在厂商侧存住**：下次同样前缀进来，**跳过重算它的 prefill，直接复用存好的 K/V**，只需 prefill 那句变化的用户问题。它本质就是第 13 篇的 KV Cache——只不过从「**一次请求内部**复用」升级成了「**跨请求**持久复用」。Anthropic 对命中的前缀 token 打骨折价（省约 90%），顺带 prefill 更短、首 token 更快。

**这里要立刻拨正一个惯性。** 你刚学完 L2 语义缓存「认意思、差不多就命中」，别把这个直觉代进来——prompt caching **正好相反**：它认**字节**，而且只认**前缀**。前缀里改一个字，从那往后存好的 KV **全部作废**（所以它跟 L1 精确缓存是一类，都认字节；也所以动态内容千万别塞前缀，否则永远命不中）。而且它有两条硬门槛：前缀得**够长**（太短厂商根本不给缓存），缓存还**有较短的存活期**（被命中才续期）。合起来意味着：它只在「**长前缀 + 请求密到能在缓存过期前复用**」时才真省 90%——低频调用可能根本命不中，别把 90% 当稳赚。

注意它省的**不是**「整个模型别跑了」——模型照跑、答案照新生成。锁死这张对照，别再混：

| | 响应缓存（你的 harness） | prompt caching（厂商侧） |
|---|---|---|
| 缓存什么 | 最终**答案** | 前缀的 **KV** |
| 命中后 | 模型**完全不跑** | 模型**照跑**，只跳过前缀 prefill |
| 治什么 | 同一个问题重复问 | **不同问题、共享长前缀** |
| 住哪 | 你的网关 / 应用层 | 模型推理引擎侧 |

两者**正交、可叠加**：热门原题走响应缓存（模型都不惊动）；长前缀的新问题走 prompt caching（省重算 prefill）。

![两种缓存对照图：左右两栏。左栏「响应缓存（住你的 harness）」：请求 → 命中则直接返回存好的答案，一条虚线绕过「模型」方框，标注「模型完全不跑 · 治同一个问题重复问」。右栏「prompt caching（住厂商推理侧）」：请求的 prompt 拆成「固定长前缀（system + 工具 + 资料）」+「变化的用户问题」，前缀部分标「复用存好的 KV，跳过重算 prefill（回扣13）」，问题部分标「照常 prefill」，模型方框照常运转、生成新答案，标注「模型照跑 · 治不同问题共享长前缀 · Anthropic 前缀 token 省约90%」。底部一行：两者正交可叠加。](assets/img/28-two-caches.svg)

## 八、管总量：预算三件套

缓存、降级、路由，全是「**每次调用省一点**」。但成本工程还缺一道**管总量的闸**。给你个吓人的场景：

> 你缓存做得再好，一个 Agent 撞进**死循环**（回扣第 24 篇祸一「炸」），或一个用户拿脚本**狂刷**——它们每次调用都不重复、缓存全 miss，一晚上给你烧出**几万块**账单。

「每次省一点」救不了你，因为病在**总量失控**。你后端防「一个用户吃垮资源」的那套，搬过来就是**成本三件套**：

- **① 计量（metering）**：你要「给个最大消耗量」，前提是**先量得出现在消耗了多少**。每次调用的 token 按类分档算钱——**输入、输出、缓存命中各是不同单价**（输出通常贵好几倍），别用一个单价拍平——再记到哪个用户 / 哪个应用头上。量不出来，就谈不上限。
- **② 配额（quota）**：per-user / per-app / per-day 的上限，撞上了就拦。
- **③ 告警（alerting）**：在账单砸下来**之前**就抓住异常（消耗速率突然飙升），而不是第二天看账单哭。

这里有个漂亮的收口，把两半篇焊在一起：**正常用户**撞到预算上限那一刻，你**未必**只能一刀切甩他 `429`。你还有上半篇那个更优雅的动作——把他**从 Opus 降到 Haiku**（回扣降级链 + 第 26 篇模型档轴），让他**还有得用、只是用差一点**。**预算撞顶，就是降级链的第三个扳机。**

但要分清对象：**撞顶降级只对正常用户成立**（还想用、只是暂时省着点用）。对本节开头那种**死循环 / 脚本狂刷 / 攻击**——降到 Haiku 救不了你，它还在刷，只是每次便宜点、死循环照烧。对这类异常来源，正确动作是**硬拦 / 按来源熔断**，不是降级。降级治的是「正常用户超支」，硬拦治的是「总量被滥用打爆」，别混。

最后是层次问题。计量 / 配额 / 告警该住哪？回扣第 27 篇——它们就是**横切治理层**那 90% 的「老朋友」（认证 / 限流 / 日志 / 算账），一点不 LLM 特殊，只是把 API Gateway 早就在做的治理，**对准了 token 花销**。所以它住**网关的横切治理层**，天然该在那儿：每个请求都过网关，账在一处看得全。

至此，这一篇的两半各归各位，全落回第 27 篇那张网关解剖图：

- **韧性**（重试 / failover / 降级链 / 熔断）→ 住**控制流层**。
- **成本治理**（计量 / 配额 / 告警）→ 住**横切治理层**。
- **缓存**这把武器最特别——它**脚踏两层**：作为降级链档 3 它是控制流层的应急手段，作为省钱正职它是**应用 / 网关层**的成本武器（就是第七节对照表里「住哪」那一栏）。

## 九、收口：老武器，新账单

第五阶段问的是「怎么把 AI 系统的架构搭对」。这一篇给的是韧性和成本这两根支柱，而它的骨架**全是你后端老规矩的平移**：

> 下游会抽风 → 老武器四件套（重试 / failover / 降级 / 熔断）搬进**网关控制流层**，每件多挂一条 LLM 新税（算钱账 / 防副作用 / 换厂商即降级 / 半开探针也花钱）→ 请求量成本变真问题 → 缓存的正职是**省钱**：精确缓存认字节有裂缝 → 语义缓存认意思（回扣 19），但反义句坑逼出**阈值旋钮**（拿第 22 篇评估定）→ 不是所有请求都配缓存（个性化 / 时效不能，稳定 + 高频才行，回扣 26 二八）→ prompt caching ≠ 响应缓存（回扣 13 KV，一个省重算一个免跑）→ 管总量靠**预算三件套**（计量 / 配额 / 告警，撞顶就降级，住横切治理层，回扣 27）。

一句话钉死这篇的纪律：

> **韧性和成本工程里没有 LLM 专属的新魔法，全是后端祖传武器。** 唯一变的，是每扣一次扳机你都得多问一句——**这一下值不值这个钱、会不会把世界改两次、认不认得出这是同一个问题。**

下一篇，我们收一收前面所有优化埋下的一个隐患：你改了缓存阈值、换了个降级策略、甚至只是把 prompt 改了一个字——**怎么知道系统没有偷偷变差？** 也就是 AI 系统的**测试与持续交付**：prompt 改一个字，怎么保证没有 regression。

## 小结

- **核心直觉（后端迁移）**：韧性四件套和缓存全是你搭后端时的祖传武器，这一篇不发明新东西，只讲搬到 LLM 时每件多挂的那条「新税」。
- **重试**：三样变了——钱（每次都花）、时间（慢 + 退避让用户干等）、结果（不幂等）。真牙齿是**计费的半截生成** + **副作用重复**（回扣 24）。错误分类跟后端一样：429/500 可重试，400 别试，带副作用的慎试。
- **failover 与降级链**：换厂商**不是平移是降级**（异构模型质量跳变，回扣 27）。降级链四档（滑模型档回扣 26 → 换厂商 → 缓存 → 兜底话术），共同规律「守住可用、牺牲质量」，永远从降得最少那档往下摔。注意分清两条轴：触发这条链的**事件**有仨（熔断跳闸 / 厂商挂了 / 预算撞顶），failover 是链上档 2 的**响应动作**、不是扳机。
- **熔断**：别一次次撞已知的死墙。三状态：闭合放行、断开跳闸（不再撞墙直接降级）、半开放一个探针试探恢复。
- **缓存正职 = 省钱**：性能是搭赠。精确缓存认字节，「什么是 RAG / RAG 是什么」会 miss → **语义缓存**认意思（把第 19 篇语义搜索对准缓存）。
- **语义缓存的坑**：反义句余弦高（退款 / 不退款），命中错答案比 miss 严重得多（省钱省出无声事故）。旋钮 = **相似度阈值**，拿第 22 篇黄金集扫**命中率 vs 错误命中率**来定。生产用 **L1 精确 + L2 语义**两层，把风险锁进 L2。
- **可缓存性**：个性化 + 时效性请求本质不该缓存（key 会带上永远在变的东西）。适合缓存 = **答案稳定 + 高频重复**（回扣 26 二八）。但「稳定」是相对的——底层一改缓存就**脏**，得配失效策略（TTL / 主动按 key·标签清），脏缓存同样会「省钱省出事故」。
- **prompt caching ≠ 响应缓存**：响应缓存存**答案**、命中则模型不跑、治重复问题；prompt caching 存**前缀 KV**、模型照跑只省重算 prefill、治共享长前缀（回扣 13）。正交可叠加。
- **管总量 = 预算三件套**：计量（先量得出，输入/输出/缓存分档单价）→ 配额（上限）→ 告警（提前抓）。**正常用户**撞顶就降级不硬拒；**死循环 / 滥用**这类异常来源则要硬拦 / 按来源熔断，降级救不了总量失控。住**网关横切治理层**（回扣 27），因为它就是 API Gateway 的治理对准了 token 花销。
