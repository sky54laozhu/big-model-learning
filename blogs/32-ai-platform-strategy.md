# AI 平台战略：治理、多租户与演进 —— 从一个功能，到一个公司的 AI 能力

> 一个全栈工程师的大模型学习笔记（三十二 · 完结）

前面 31 篇，你都在盖**同一样东西**：一个 AI 功能。从「文字怎么变数字」一路到网关、路由、韧性、测试、安全、可观测性——你亲手把一个能上线的 AI 系统，从地基垒到了屋顶。

这最后一篇，视角要抬起来一档：从「**一个功能**怎么搭对」，抬到「一个**公司**的 AI 能力怎么长起来」。

老规矩，从一个你闭眼就能预见的烂摊子切进去。

---

## 一、锚一个烂摊子：8 个团队各干各的

公司火了，8 个团队都要上 AI：客服要做工单自动回复、电商要做商品描述、风控要做欺诈解释、法务要做合同审查……

**如果什么都不管**，让这 8 个团队各自照着前面 26–31 篇，从零搭一套自己的——网关、路由、eval、密钥管理、监控，一人一套。会长出哪些烂摊子？凭你的后端老经验，一列一大把：

- **重复造轮子**：8 套网关、8 套 eval、8 份密钥管理，同一件事干了 8 遍。
- **成本算不清**：月底老板收到一张厂商的天价账单，问「这钱哪个团队花的、花在哪」——**你答不出来**。
- **安全全是洞**：8 处密钥各自保管（泄漏面 ×8）、8 个团队各自把用户隐私往第三方厂商发、某个 Agent 手里攥着 `run_sql` 万能钥匙，一个 prompt injection 就能删库（回扣 30）。
- **治理真空**：谁在什么时候、对哪个模型、做了什么操作——**没人审计得了**；某个团队偷偷用了没过合规的数据，等出事才发现。
- **殃及他人**：一个团队的失控循环烧穿了共享额度、拖垮了公共网关，另外 7 个团队跟着遭殃。

这一堆烂摊子，就是「**平台**」这个东西存在的**全部理由**。而且——它们自己就分好类了。

---

## 二、命名核心招：平台 = 网关，放大到「跨团队」

把上面那堆烂摊子归归类，你会发现它自动分成**四堆**：

| 烂摊子 | 归到哪一类 |
|---|---|
| 8 套网关 / eval / 密钥重复造 | **平台化**（要不要收口） |
| 账单算不清、说不清哪个团队花的 | **成本分摊** |
| 密钥泄漏、隐私外发、违规操作、审计缺失 | **治理** |
| 一个团队搞砸 → 殃及其他 7 个 | **多租户隔离** |

这四堆——**平台化（要不要收口）、成本分摊、治理、多租户隔离**——就是这篇的骨架。你不是在猜目录，是自己把它推出来了。（还有一面藏在「重复造轮子」里、要沿**时间轴**才看得见——模型半年一变，没平台就得 8 个团队各改一遍，这就是第五个话题「**平台演进**」，我们留到第七节再揭。这也正是标题里那个「演进」。）

而收口这堆烂摊子的核心招，**你其实早就见过**。回扣 Blog 27 网关那一篇，我们当时怎么说的——

> 「同一件横切的事，散在 N 个**调用点** → 收口成一层**网关**」。

Blog 32 干的是**一模一样**的动作，只是尺度放大了一档：

> 「同一件横切的事，散在 N 个**团队** → 收口成一个**平台**」。

网关是「一个团队内、跨调用点」的收口；平台是「全公司、跨团队」的收口。所以「8 套网关重复造」的解法几乎是自动的：**别让 8 个团队各建网关，公司建一个共享 AI 平台，大家接进来。**

![平台 = 网关放大到跨团队尺度。左边「没有平台」：8 个业务团队（客服/电商/风控/法务…）各自是一个方框，每个方框内部都重复塞着同一组红色徽章「网关·eval·密钥·账本」，各自的线路乱七八糟地连向底部三家模型厂商（Anthropic/OpenAI/GLM），线路交叉成一团，下方红字标注「同一套横切逻辑 ×8 份，密钥泄漏面 ×8，账算不清，坏邻居互相殃及」。右边「有平台」：8 个业务团队只对中间一层蓝色的「AI 平台」说话（只说统一格式），那组横切徽章收口进平台一层（绿色「收口一处：网关·路由·eval·密钥·治理·计量」），平台再统一对接三家厂商，线路清爽。底部结论「平台 = Blog 27 网关那一招，从『跨调用点』放大到『跨团队』」。](assets/img/32-mess-to-platform.svg)

想清楚了这一招，剩下的活分两种：一种是**后端老本行**，原样搬过来就行；另一种是 **AI 独有的新税**，老办法直接套会翻车。这篇的策略是——老问题一笔带过，火力全压在新税上。

## 三、先把老问题一笔带过

四堆里，有一大半是你后端时代天天在解的，换成 AI 平台**没啥新鲜**：

- **重复造轮子** → 平台收口，上面刚说完。
- **密钥管理** → secrets manager，谁能取、怎么轮转，老问题。
- **审计** → 每个操作落一条 audit log，谁在什么时候干了什么，老问题。
- **权限 / 违规** → IAM / RBAC / policy-as-code，谁能访问什么资源，老问题。
- **基本的租户隔离** → `tenant_id` 加一列、行级权限、按租户限流，经典 SaaS 老问题。

这些，你照着后端的成熟做法搬就行，不展开。真正值得单写的，是套上老办法会**翻车**的两条新税——它们都源自同一个根：**LLM 平台共享的，不只是算力，还有「语义」。**

---

## 四、⚠️ 新税一：多租户的「语义串味」通道

经典 SaaS 多租户为什么闭眼能解？因为数据各在各的行里，加个 `tenant_id`、行级权限一卡，**井水不犯河水**。数据是「死」的，待在它该待的格子里，不会自己跑出去。

但 AI 平台引入了几样经典 SaaS 里**根本不存在的共享状态**——而且是**语义**状态，会串：

**① 共享语义缓存（回扣 Blog 28）。** 租户 A 问「我们公司 Q3 的财报数字是多少」，答案进了共享语义缓存。租户 B 问一句语义相近的，**命中了 A 的缓存** → A 的私密数据，直接串给了 B。

这是致命的地方：经典缓存按 key **精确匹配**，加个 `tenant_id` 前缀就隔离得干干净净；语义缓存是**模糊匹配**，它认的是「意思像不像」，`tenant_id` 前缀那套救不了它——两个租户问了「意思相近」的问题，缓存就把一个人的答案喂给了另一个人。**这条串味通道，是 LLM 独有的。**

**② 共享 RAG 知识库（回扣 Blog 20/21）。** 全公司一个向量库，租户 A 的查询在检索时召回了租户 B 的文档 → 跨租户数据泄漏。

这里有个认知要翻转：单团队时，我们（回扣 Blog 21）把「向量库的 metadata `WHERE` 过滤」当成一项**普通的检索约束**——只在「这个用户的 / 某个时间段的」文档里搜，顺带缩小范围。到了多租户平台，`tenant_id` 的 metadata 过滤**升级成了安全边界**——它不再是「顺带把范围缩小一点」，而是「漏一条就是数据事故」。同一个技术，尺度一变，性质从一项普通约束变成了红线。

一句话收口：

> **经典 SaaS 只共享算力；AI 平台还共享了「语义」（缓存、向量、上下文），而语义是模糊的、会串的。**

所以多租户隔离要从「按 key / 按行隔离」升级成「**按语义空间隔离**」——注意这跟上面「`tenant_id` 前缀救不了」不矛盾：救不了的是把 `tenant_id` 拼进被匹配的**查询文本**再做模糊匹配（意思还是会撞）；有效的是**给每个租户切一块独立的检索 / 缓存空间，让相似度匹配根本不跨租户**。落到实处：每租户独立缓存命名空间、向量检索必须强制带 `tenant_id` 过滤且当安全边界对待。**凡是共享的语义状态，都要问一句：它会不会串味？**

## 五、⚠️ 新税二：成本，从「资源依赖」变成「行为依赖」

计量单位从「CPU 小时 / GB」换成「token」——这一步其实还好。真正的新麻烦有两条。

**① token 成本是「行为依赖」，不是「资源依赖」。** 云成本你 provision 了多少 CPU 就是多少，**确定的**、可预估。AI 成本取决于模型每次**怎么答**：同一句问话，走 Opus 还是 Haiku（同代）差 5 倍（回扣 26）、走没走缓存差一截、级联试了几次（回扣 28）……账单能差好几倍。你没法像云那样「按配额预估」，只能**按实际 token 事后计量**——每一次调用都得记下「哪个租户、哪个模型、输入 / 输出 / 缓存各多少 token」，才算得清账（这也正是 Blog 31 可观测性里那笔成本指标的用途）。

**② 共享的东西，该算谁头上？** 这里要分两层：

- 共享网关、共享 eval 集、共享监控——这些**共享基础设施**该公摊还是按量摊，其实是云 FinOps 的**老题**（shared services 成本分摊），原样搬你的老办法就行，不新鲜。
- 真正 AI 独有的新麻烦，是 **Blog 28 的 prompt caching**（跨请求复用前缀 KV）：那段共享的系统提示词前缀，缓存**省下**的钱、**养着**它的成本，算平台的还是各租户的？云资源不共享「前缀」，AI 平台的成本却在这里**互相纠缠**——一个租户的请求命中了另一个租户养热的前缀缓存，省下的账算谁的，这是云成本分摊里没有的新题。

所以平台得设计一套**账本**：哪些进平台公摊、哪些按租户实际用量做 **chargeback**（谁用谁付）或 **showback**（不真收费，但让你看见自己花了多少）。

**③ 坏邻居烧公共预算。** 一个租户的失控循环（回扣 Blog 24「炸」）会烧掉**公共**额度，拖垮其他 7 个团队——这就是「殃及他人」的成本版。解法回扣 Blog 28：**按租户配额 + 按来源熔断**。正常用户撞顶走降级，异常来源直接硬拦——别让一个坏邻居拖垮全平台。

![AI 平台的两条新税。顶部一条灰带列出老问题（密钥 / 审计 / IAM / 基本租户隔离），标「后端闭眼解，原样搬」。下面两块橙色高亮面板。左面板「⚠️ 新税一·语义串味」：租户 A 问「Q3 财报数字」，答案进了中间的「共享语义缓存（模糊匹配）」，租户 B 问「意思相近」的问题，一条红箭头从缓存指回 B，标注「A 的私密答案 → 串给了 B，key 前缀救不了模糊匹配」；下方补「② 共享 RAG 库检索会召回别的租户文档」，并用一个黄框强调认知翻转「tenant_id 的 metadata 过滤，从『性能优化』升级成『安全边界』，漏一条 = 事故」。右面板「⚠️ 新税二·成本纠缠」三个小框：① 行为依赖非资源依赖（同一句话走 Opus 还是 Haiku 差 5 倍）；② 共享 prompt-cache 前缀的账互相纠缠该算谁（公摊 vs chargeback）；③ 红框「坏邻居烧公共预算 → 按租户配额 + 按来源熔断」。底部结论「两条新税同一个根：AI 平台共享的不只是算力，还有语义——而语义模糊、会串」。](assets/img/32-new-taxes.svg)

## 六、治理对象扩容：CI 门禁在守着谁进出？

再看「治理」这堆。经典治理你太熟：**谁能访问什么资源**（IAM / RBAC / audit log），原样搬。

但 AI 平台的治理，多出了一批经典 IAM 里**不存在**的新对象。怎么找到它们？顺着两条线索：**哪些东西「改一个字就可能让全公司行为大变」、「厂商还会背着你偷偷改」？**

你可能第一反应是「**测评 + CI 门禁**」——对，但那是治理的**机制**（回扣 Blog 22 那把尺子 / Blog 29 那道闸门），是**卡关的那道门**。真正要问的是：**这道门，在守着谁进出？** 排队过门的「货」，才是新的治理对象：

| 新的「一等治理对象」 | 为什么它得被治理 | 回扣 |
|---|---|---|
| **Prompt（提示词）** | 改一个字，全公司行为可能大变——它就是「代码」。谁能改生产 prompt？改了要过评审吗？出事怎么回滚到上一版？ | 29 |
| **模型 / 版本** | 谁有权用贵模型（Opus 要审批？）；更阴的是**厂商静默升级**，`latest` 别名背着你把模型换了 → 必须钉死版本、变更要审批 + 重跑门禁 | 26 / 29 |
| **评估标准 + 门禁** | ✅ 你答的这个。及格线定多高、黄金集谁维护——这本身也是治理决策，不是某个工程师随手能改的 | 22 / 29 |
| **数据流向** | 哪些数据能喂给第三方厂商、哪些必须脱敏、能不能出境——PII / 合规红线 | 30 |

一句话收口：

> **后端时代，进 CI 门禁的「货」基本只有代码一种；AI 平台里，prompt、模型版本、eval 标准、数据策略，全都升级成了跟代码平级的一等治理对象**——各自都要版本化、审批、回滚、审计。

你答的「测评 + CI 门禁」是那道门，而这张表，就是**排队过门的队伍**。治理 AI 平台，就是把这支队伍管起来。

## 七、平台演进：模型半年一变，冲击面 8 还是 1？

最后一个主题：**平台演进**。这个牵出这篇——也是整个系列——的收官立意。

给你个真实张力：平台建好了、8 个团队都接进来了。**半年后，模型能力大变**——新一代出来了、老模型被下线了、价格腰斩了（回扣 29，这种变动厂商说来就来）。这个冲击，砸到谁头上？

**如果没有平台：** 砸到**全部 8 个团队**。每个团队各自去改代码、重钉版本、重跑测评、重新灰度——同一件事干 8 遍（重复劳动又回来了），而且**总有团队漏改**，某天线上突然翻车（回扣 29 静默升级砸中没设防的人）。**冲击面 = 8。**

**如果有平台：** 模型变更被挡在**平台的抽象层 / 网关层**（回扣 27）。平台内部做一次升级——灰度 + 门禁把关（回扣 29），确认没 regression 再放量。上层 8 个团队面对的始终是**同一个稳定的 API**，换没换模型它们**无感**。**冲击面 = 1（平台自己扛）。**

这就是平台存在的**终极价值**，给它一个精确的名字：

> 平台 = **把「模型会抖、会漂、会被厂商偷改」这种不确定性，从各业务团队那里收上来，统一兜在平台这一层。**

而这，正是**番外 17b 柱三**的组织尺度版：**用确定的手段（灰度、门禁、版本钉死、抽象层），兜住会抖的零件（模型）。** 只不过前面几篇兜的是「一次调用 / 一次改动 / 每天运行」，平台兜的是**整个公司面对模型世界的抖动**。

这也顺带定了平台该长什么样：它不是个「代收费的中间商」，而是一条 **paved road（铺好的路）**——把 26–31 篇那些最佳实践（网关、路由、韧性、测试、安全、观测）固化成平台的**默认能力**，业务团队走上来就自带一整套，不用各自重新发现、重新踩坑。平台的价值不在「管住谁」，而在「让每个团队默认就做对」。

## 八、收官合龙：平台，就是组织尺度的 harness

四堆烂摊子 + 沿时间轴的平台演进，全推完了。退一步，看这整个系列的暗线在这里怎么合龙。

从番外 17b 起，我们一直在讲工程的**三根柱子**。回头看这条弧线——三根柱子，一路从「一个功能」放大到「一个公司」：

| 柱子 | 特性尺度（前 31 篇） | 组织尺度（本篇平台） |
|---|---|---|
| **柱一 · 约束下权衡** | 每一次技术选型 | 自建 vs 托管、共享 vs 隔离、公摊 vs chargeback |
| **柱二 · 可复用纪律** | 一个 harness 内的零件复用 | **paved road**：把 26–31 的最佳实践固化成平台默认 |
| **柱三 · 驯服不确定性** | 18 单次校验 / 29 发布回归 / 31 运行观测 | **平台替全公司兜住模型抖动** |

看最右一列——**平台，就是「harness」这个词放大到组织尺度的样子。**

前面 31 篇，你在给**一个功能**盖 harness：用确定性代码，把一个会抖的模型兜成一个可靠的功能。这最后一篇，是一个**公司**在给自己的 AI 能力盖 harness：用一层平台，把「模型世界的抖动」兜成上层团队可以放心依赖的稳定能力。**同一套工程思维，从一行代码，长到了一个平台。**

而这，正好呼应整个系列的起点。Blog 01 我们从「一个人怎么理解一个概率函数」出发——`f(x)`，冻死的、会抖的、只会算下一个 token 的那个函数。走到 Blog 32，我们在问「一个公司怎么把成千上万次这样的函数调用，组织成一种可持续、可治理、能长期演进的能力」。

**技术是同一套技术，工程是同一套工程，变的只是尺度。**

从 `if-else` 到概率预测，从一个 token 到一个平台——这套「懂原理 → 会盖楼 → 能规模化」的能力，你现在都有了。

## 小结

- **核心直觉（后端迁移）**：一个公司全员上 AI，如果各团队各干各的，必然长出四堆烂摊子——重复造轮子 / 成本算不清 / 安全治理真空 / 互相殃及。这四堆 = 四个话题（平台化 / 成本分摊 / 治理 / 多租户），再加一面沿时间轴展开的**平台演进**。
- **命名核心招**：平台 = **Blog 27 网关那一招放大一档**——「同一件横切的事散在 N 个**团队** → 收口成一个平台」。老问题（密钥 / 审计 / IAM / 基本租户隔离）原样搬，火力压在 AI 新税上。
- **⚠️ 新税一 · 语义串味**：经典 SaaS 只共享算力，AI 平台还共享**语义状态**——共享语义缓存（回扣 28，模糊匹配把 A 的私密答案串给 B）、共享 RAG 库（回扣 20/21，检索召回别的租户文档）。隔离要从「按 key / 行」升级成「按语义空间」；`tenant_id` 的 metadata 过滤从**优化**升级成**安全边界**。
- **⚠️ 新税二 · 成本纠缠**：token 成本是**行为依赖**非资源依赖（同一句话走不同模型差数倍，回扣 26/28），只能事后按量计；共享 prompt-cache（回扣 28）的账**互相纠缠**，得设计公摊 vs chargeback 账本；坏邻居烧公共预算 → 按租户配额 + 按来源熔断（回扣 24/28）。
- **治理对象扩容**：CI 门禁是**门**（回扣 22/29），排队过门的新一等治理对象 = **prompt / 模型版本 / eval 标准 / 数据流向**（回扣 29/30）——后端只治代码一种，AI 平台要把这四样都版本化、审批、回滚、审计。
- **平台演进**：模型半年一变，**没平台冲击面 = 8**（各团队各改、总有漏、静默升级砸中没设防的），**有平台冲击面 = 1**（挡在抽象层，平台灰度 + 门禁内部消化，上层无感）。平台 = 把「模型抖动」这种不确定性从各团队收上来兜在一层 = **柱三的组织尺度版**；形态是一条 **paved road**，让每个团队默认就做对。
- **harness 暗线（全系列合龙）**：三根柱子一路从特性尺度放大到组织尺度——**平台 = 组织尺度的 harness**。前 31 篇给一个功能盖 harness，这一篇一个公司给自己的 AI 能力盖 harness，同一套工程思维只是尺度不同。呼应 Blog 01 那个会抖的 `f(x)`：**技术是同一套技术，工程是同一套工程，变的只是尺度。**
